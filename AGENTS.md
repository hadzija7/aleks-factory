## Project: Aleks Factory

Kanban board (Next.js 16, App Router, Tailwind 4) that hands tasks to a Mozaik agent (`@mozaik-ai/core`).

- Dev: `pnpm dev` · Verify: `pnpm lint && pnpm typecheck && pnpm build` · Test: `pnpm test` (vitest; sandbox tests need Docker + the sandbox image)
- Projects and tasks persist in `data/projects.json` / `data/tasks.json` (gitignored) via `src/lib/project-store.ts` / `src/lib/task-store.ts` (shared `json-store.ts`).
- Each project is a local git repo at `data/projects/<id>/repo`, bootstrapped with create-next-app in Docker (`src/lib/workspace.ts`). Each task gets branch `task/<id8>` + worktree `data/projects/<id>/worktrees/<taskId>`; host git always passes `--git-dir`/`--work-tree` explicitly and disables hooks/fsmonitor because agents control worktree contents. Done tasks are reviewed in the diff viewer and committed + merged into main from the UI (`/api/tasks/[id]/diff`, `/commit`).
- Previews (`src/lib/preview.ts`) run `npm run dev` for a task worktree or main in a Docker container on a random localhost port. `node_modules` (per checkout) and the npm cache live in Docker volumes (`aleks-factory-nm-*`, `aleks-factory-npm-cache`) because bind-mounted installs on macOS take minutes. Containers carry an owner-pid label; startup only removes containers whose owner process is dead.
- `data/` is excluded from tsconfig, eslint and vitest (`pnpm test` runs `vitest run src`).
- Moving a task to `in_progress` (PATCH `/api/tasks/[id]`) calls `executeTask` in `src/lib/agent.ts`: the "Kanban Board" human sends a `task.assigned` event, the "Task Executor" agent reacts with `runLoop`, and the board marks the task `done`/`failed` on `model.answer`.
- Env: `OPENAI_API_KEY` (or the provider key for `MOZAIK_MODEL`, e.g. `CURSOR_API_KEY` for `composer-2.5`), see `.env.example`.
- Models: each model-calling agent (`implement`, `review`; `merge` is git-only) has its own provider + model, set on `/settings` ("Factory settings", `/api/settings`) and stored in `data/agent-models.json` (`src/lib/agent-models.ts`). Agents without a setting use `MOZAIK_MODEL`. The model is resolved at the start of every agent run (`startRun` in `agent.ts`), so saved changes apply from the next run. Lookups go through the factory registry in `src/lib/models.ts` (Mozaik's `supportedModels` grouped by provider, plus `FACTORY_PROVIDERS` for factory-implemented endpoints `cursor` / `composer-2.5`). Saves are rejected for unknown models or models missing a capability the agent needs (`requires` in `factory-agents.ts`). The settings API only reports whether a provider's credential env var is set, never its value.
- Cursor provider (`src/lib/providers/cursor.ts`): Composer through `@cursor/sdk` (`CURSOR_API_KEY`; the SDK owns endpoint and auth, `Agent.prompt` has no base URL option; it is a `serverExternalPackages` entry). Each `infer()` is one `Agent.prompt()` with the Mozaik tools as `local.customTools` (calling `tool.invoke`), so Cursor runs the tool loop and `infer()` returns one final `ModelMessageItem` + `TokenUsage`. `tools: ["mcp"]` keeps only the MCP family, which is how custom tools are called (`tools: []` would remove them too); `local.fs: emptyFs()` keeps host files, shell, hooks and git status away from the model; `settingSources`/`mcpServers` stay unset so no ambient rules or MCP servers load. Context is flattened into one prompt. Structured output is emulated with a `submit_result` custom tool whose args are validated against the schema (ajv; errors go back to the model) and become the answer JSON. Tool results are capped at 30k chars (the SDK spills MCP results over 40 KB to a file the model can't read). Tool calls are `execute_tool <name>` spans under the chat span (`AgentRun.current()` / AsyncLocalStorage set by `modelTurn`, explicit call id per call); Mozaik `function_call.*` events (activity feed rows) don't fire for this model. Composer's context window isn't published, so its spec says 0 (unknown) and the settings UI shows no context size.
- Mozaik is pinned to stable 4.1.0 (event-driven runtime: `defineRuntime`, `createAgent`, `createHuman`, `runLoop`). `runLoop` emits no error event, so a custom `InferenceRunner` in `agent.ts` turns inference errors into failures.
- Agent tools live in `src/lib/coding-tools.ts` (`createCodingTools(root)` returns Mozaik `FunctionTool`s: `list_files`, `read_file`, `edit_file`, `write_file`, `run_command`). Every path is confined to the task's worktree, and `.git` is off-limits. Tools throw on errors, and Mozaik's `DefaultFunctionCallRunner` sends the error back to the model as text.
- `run_command` runs in `src/lib/docker-sandbox.ts`: one container `agent-<taskId>` per task session (`--network none`, only the project root mounted at `/work`, 1 CPU / 1 GB / 256 pids, 60s timeout). It is removed when the task finishes, on process exit, and stale `agent-*` containers are removed on startup. Image: `AGENT_SANDBOX_IMAGE` (default `node:22-bookworm`).
- Review loop: when the executor answers, the board moves the task to `in_review` and emits `task.review_requested`; the "Code Reviewer" agent (read-only tools + `run_command`, structured output `{verdict, summary, findings}`) answers, then the board moves the task to `done` or back to `in_progress` (re-emitting `task.assigned` with `task.review`). After `MAX_REVIEW_ROUNDS` (default 3) fix rounds it fails. One sandbox per task, shared by both agents.
- Merge conflicts: after the executor answers and again on approval, `syncWithMain` (`workspace.ts`) snapshots the worktree as a WIP commit and merges main into the task branch. Conflicts leave the merge in progress (markers in the files), set `task.conflicts` and go back to the executor as a rework round (card shows "Resolving merge conflicts"); the next sync concludes the merge once no conflicted file has markers. Done tasks are kept mergeable and green (like PRs with CI): after every merge into main, `syncDoneTasks` (`agent.ts`) merges main into each other done task, then re-runs lint + typecheck (plus `npm install` if package files changed) in an `agent-check-<id>` sandbox. Conflicts or failing checks send it back with a fresh round budget (`task.rework` = `conflicts`/`checks` drives the labels); if the checks can't run (no exit code / timeout) it stays done. While re-checking, the card shows the step from the in-memory `task-checks.ts` label (`task.checking`, added by `getTask`/`listTasks`), and `isTaskBusy` blocks moving, deleting and committing it. `/commit` syncs too (a conflict there resets rounds and sends the task back), then `reset --soft main` squashes the branch into one commit with the user's message before the `--no-ff` merge.
- Observability: when `MOZAIK_API_KEY` is set, `ensureRuntime` joins a `@mozaik-ai/cloud-sdk/exporter` participant that streams every runtime event to app.jigjoy.ai (one cloud session per server process; the live link is logged on first task). `MOZAIK_REDACTION` controls how much content is sent.
- Tracing (`src/lib/tracing.ts`): when `DASH0_OTLP_ENDPOINT` + `DASH0_AUTH_TOKEN` (optional `DASH0_DATASET`) are set, every agent run (implement / review, plus the merge in `/commit`) is an `AgentRun`: its own OTel `TracerProvider` exporting OTLP/HTTP to Dash0, a root `invoke_agent` span, a `chat` span per inference (model + token counts, wrapped in `inferenceRunner`) and an `execute_tool docker_exec` span per `run_command` (call id from `function_call.started`). Tool spans started inside a chat or tool span nest under it and inherit its call id (the Cursor provider runs tools inside `infer()`). Session/VCS/`user.name` attributes go on the resource and every span; VCS comes from `taskVcs` (task branch, HEAD, project `origin`, falling back to this repo's origin). Never add prompts, messages or tool I/O to spans. Dash0 Insights only lists sessions whose instrumentation scope is `dash0-agent-plugin` (verified with probes), so keep that tracer name; `DASH0_HARNESS_NAME` overrides `gen_ai.harness.name` (default `mozaik`).
- Secrets: agents write them to `.env.local` in the checkout (instructions in `agent.ts`). Gitignored root `.env*` files are synced by `workspace.ts` (main -> new worktree, main -> worktree missing keys only on every `syncWithMain`, worktree -> main on merge, key-level merge, symlinks skipped). `worktreeGit` runs one command at a time per worktree to avoid `index.lock` races and only their key names are shown in the diff viewer.
- Agent network: sandboxes join the `--internal` Docker network `aleks-factory-sandbox`; their only way out is the shared `aleks-factory-egress` proxy container (`docker/egress-proxy.mjs`, recreated when the script hash changes, not removed by per-process cleanup). `src/lib/egress.ts` gives each task session a proxy token whose allowlist is `DEFAULT_ALLOWED_DOMAINS` (npm registry) + the project's `allowedDomains` (edited on the project page), stored in `data/egress/allowlist.json`. CONNECT is limited to port 443. If the proxy can't start, sandboxes fall back to `--network none`.
